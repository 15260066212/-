# ADR-007: 认证机制（API Key + 密码登录 + 开发模式降级）

**Type:** ADR
**Status:** accepted
**Tags:** security, authentication, api-key, password

## Context

GEO 系统作为多用户内容发布平台，需要一套安全、灵活且易于集成的认证机制来控制 API 访问权限。核心约束与挑战如下：

- **多端接入**：系统同时服务于 Web 前端（浏览器登录）、第三方集成（API 调用）和内部服务（服务间调用），不同场景的认证诉求不同；
- **部署模式多样**：本地开发、Docker 部署、内网部署、SaaS 化等场景对认证强度的要求差异很大；
- **向后兼容**：早期版本无认证机制（dev mode），需要平滑过渡到强制认证而不破坏现有部署；
- **存储约束**：基于 SQLite，认证数据持久化需与现有 `users` 表结构一致，不引入额外的认证服务依赖；
- **平台凭证 vs 用户凭证**：用户登录凭证（账号密码）与各内容平台的发布凭证（Cookie/Token）是两个完全不同的概念，必须明确区分。

## Decision

采用**三层认证架构**，以 API Key 为主要认证方式，密码登录为辅助手段，开发模式降级为兜底方案。

### 1. 认证方式分层

| 认证方式 | 使用场景 | 传递方式 | 安全性 |
|----------|----------|----------|--------|
| **API Key** | 第三方集成、服务间调用、前端鉴权 | `x-api-key` 请求头 或 `Authorization: Bearer <key>` | 中高（密钥随机生成，不可猜测） |
| **密码登录** | Web 前端用户登录 | `POST /api/auth/login` + JSON Body | 中（SHA-256 哈希存储，建议配合强度要求） |
| **开发模式降级** | 本地开发、单用户部署 | 无凭证，默认以 `user_default` 身份访问 | 低（仅适用于可信环境） |

### 2. API Key 认证流程

API Key 是系统的**主要认证方式**，所有需要鉴权的 API 路由都通过 `createAuthMiddleware` 中间件进行统一校验：

1. **请求头解析**：中间件依次尝试从 `x-api-key` 和 `Authorization: Bearer <key>` 两种方式提取 API Key；
2. **用户查找**：调用 `db.users.getUserByApiKey(apiKey)` 在 `users` 表中查找对应用户；
3. **上下文注入**：找到有效用户后，通过 `c.set('user', user)` 将用户对象注入 Hono 上下文，下游路由通过 `c.get('user')` 获取当前用户；
4. **活跃时间更新**：每次有效请求都会调用 `updateUserLastActive()` 更新用户最后活跃时间；
5. **未授权响应**：API Key 无效或缺失（且强制认证模式开启）时返回 `401 Unauthorized`。

### 3. 密码登录流程

密码登录仅用于 Web 前端的用户身份验证，登录成功后返回 API Key 供后续请求使用：

1. **登录接口**：`POST /api/auth/login` 接收 `{ username, password }`；
2. **密码校验**：使用 SHA-256 哈希与数据库中存储的 `passwordHash` 比对；
3. **登录响应**：校验通过后返回用户基本信息 + `apiKey`，前端将 API Key 存储在本地用于后续请求；
4. **验证接口**：`POST /api/auth/verify` 用于前端校验当前登录态是否有效；
5. **登出接口**：`POST /api/auth/logout` 当前为无状态实现（前端清除本地存储的 API Key 即可）。

### 4. 开发模式降级

当 `AUTH_REQUIRE_API_KEY` 环境变量未设置为 `'true'` 时，系统运行在**开发兼容模式**：

- 未携带 API Key 的请求自动以 `user_default`（默认管理员）身份执行；
- 携带有效 API Key 的请求仍会正常解析为对应用户；
- 此模式保证了从无认证版本到有认证版本的平滑升级，不破坏现有部署；
- **生产环境必须显式设置 `AUTH_REQUIRE_API_KEY=true`** 以启用强制认证。

### 5. 用户与权限模型

用户数据存储在 `users` 表中，核心字段：

| 字段 | 说明 |
|------|------|
| `id` | 用户唯一标识（`user_` 前缀） |
| `username` | 登录用户名（唯一） |
| `displayName` | 显示名称 |
| `passwordHash` | SHA-256 密码哈希 |
| `apiKey` | 随机生成的 API Key（`geo-` 前缀） |
| `role` | 用户角色（`admin` / `user`） |
| `lastActiveAt` | 最后活跃时间 |
| `createdAt` | 创建时间 |

当前角色权限为**单管理员 + 普通用户**两级模型，后续可扩展为 RBAC。

### 6. 平台凭证与用户凭证的分离

系统中存在两种完全不同的凭证体系，必须明确区分：

- **用户认证凭证**（本 ADR 范围）：用于用户登录 GEO 系统、调用 GEO API，包括用户名/密码、API Key；
- **内容平台凭证**（非本 ADR 范围）：用于在各内容平台（微信公众号、知乎等）上发布文章，包括 Cookie、Session、API Token 等，存储在 `credentials` 表中，由 `PlatformCredentials` 类型描述。

两者在数据库中分别存储在 `users` 表和 `credentials` 表，通过用户 ID 关联。

## Alternatives Considered

### 替代方案 1：JWT Token 认证

**描述**：使用 JSON Web Token 替代 API Key，登录后签发带过期时间的 Token。

**否决理由**：
- GEO 主要服务端到端 API 调用和单页应用，无分布式会话共享需求；
- JWT 无法主动吊销（除非引入黑名单机制，复杂度上升）；
- API Key 实现更简单，且已满足安全需求；
- 当前用户量小（< 100），无 JWT 的扩展性收益。

**保留可能性**：未来如果需要多节点部署、细粒度会话控制或 SSO 集成，可迁移到 JWT。

### 替代方案 2：Session + Cookie 认证

**描述**：传统服务端 Session 方案，登录后写入 Session，浏览器通过 Cookie 携带 Session ID。

**否决理由**：
- 系统同时需要支持 API 集成场景，Cookie 方式对非浏览器客户端不友好；
- 前后端分离架构下，API Key / Bearer Token 模式更通用；
- Session 需要服务端状态存储，与 SQLite + 单实例架构不匹配。

### 替代方案 3：OAuth 2.0 / OIDC 单点登录

**描述**：集成第三方身份提供商（如企业微信、飞书、GitHub）实现 SSO。

**否决理由**：
- 当前阶段为早期产品，用户量小，自建认证足够；
- 引入 OAuth 依赖会增加部署复杂度和外部依赖风险；
- 目标用户（内容运营人员）不一定有企业 SSO 账号。

**保留可能性**：企业版或 SaaS 化时可作为高级功能引入。

### 替代方案 4：bcrypt / Argon2 密码哈希

**描述**：使用 bcrypt 或 Argon2 等慢哈希算法替代 SHA-256 存储密码。

**否决理由**：
- 当前使用 SHA-256 + 无盐，安全性有局限，但考虑到：
  - 系统为内部工具/小范围部署，攻击面有限；
  - 用户自主设置密码，非大规模用户系统；
  - SQLite 环境下引入 bcrypt 需额外 native 依赖。
- 作为短期方案可接受，但长期应升级。

**保留可能性**：1.0 版本前应迁移到 bcrypt，已标记为技术债务。

## Consequences

### 正面影响

1. **实现简单**：API Key + 中间件模式代码量小，易于理解和维护；
2. **兼容性好**：开发模式降级保证了平滑升级，不破坏现有部署；
3. **多场景适用**：同时支持前端登录和第三方 API 集成；
4. **无状态易扩展**：API Key 存储在数据库中，不依赖服务端内存状态；
5. **统一入口**：所有认证逻辑收敛到 `createAuthMiddleware`，便于审计和修改。

### 负面影响

1. **密码哈希强度不足**：SHA-256 无盐哈希对抗彩虹表攻击能力弱，需尽快升级为 bcrypt；
2. **无 API Key 权限粒度**：当前 API Key 等同于用户全部权限，无法限制为只读或特定操作；
3. **无 API Key 过期机制**：API Key 永久有效，丢失后需手动吊销，存在安全风险；
4. **无登录限流**：密码登录接口无速率限制，存在暴力破解风险；
5. **单设备登录**：一个用户只有一个 API Key，多设备登录会互相踢下线。

### 需要跟进的事项

- [ ] 密码哈希从 SHA-256 迁移到 bcrypt（安全债务）
- [ ] 增加登录失败次数限制和速率限制
- [ ] 支持 API Key 过期时间和手动吊销
- [ ] 支持多 API Key（命名 + 权限粒度）
- [ ] 增加审计日志（登录、登出、API Key 变更）

## Superseded when

当出现以下任一情况时，本决策应被重新评估：

1. 用户规模超过 500 人或需要企业级 SSO 集成；
2. 需要细粒度 API 权限控制（按接口、按资源）；
3. 部署为多节点集群，需要分布式会话管理；
4. 安全审计要求使用 bcrypt/Argon2 等强密码哈希；
5. 引入移动端 App 或第三方 OAuth 登录需求。
